System Architecture Overview

Next.js monorepo — one codebase, two distinct surfaces (guard mobile + manager desktop)

Frontend

Next.js 14 (App Router)

  • /guard/* — mobile-first RTL guard portal
  • /manager/* — desktop manager dashboard
  • /auth/* — login, invite accept
  • Tailwind CSS + shadcn/ui
  • Hebrew RTL (dir="rtl" on html, Tailwind RTL plugin)
Backend (API Routes)

Next.js API Routes

  • /api/auth/* — NextAuth session handling
  • /api/periods/* — scheduling period CRUD
  • /api/availability/* — guard submissions
  • /api/schedule/* — generate, read, update draft
  • /api/admin/* — courts, guards, config
Scheduling Engine

Server-Side TypeScript Module

  • Runs entirely on the server (no edge runtime)
  • Pass 1: Constraint-aware slot filling
  • Pass 2: Weekly minimum enforcement
  • Pass 3: Fairness rebalancing + opening duty
  • Returns draft + structured warnings list
Data Layer

PostgreSQL + Prisma ORM

  • Hosted on Neon (serverless PostgreSQL, free tier) or Railway
  • Prisma for type-safe queries and schema migrations
  • All scheduling history stored for cross-period fairness
  • NextAuth adapter uses the same DB

Request Flow

Guard (Phone) → Next.js Page (RSC) → API Route → Prisma → PostgreSQL
Manager triggers Generate → API Route → Scheduling Engine (3 passes) → Draft saved to DB → Manager reviews
No microservices, no separate backend. Everything runs in one Next.js app. The scheduling engine is a TypeScript module called from an API route — not a separate service. This keeps deployment simple (single Vercel or Railway project) and is perfectly adequate for 150 guards running schedules a few times per day.
