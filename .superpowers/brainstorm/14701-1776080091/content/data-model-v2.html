Data Model — Clarified

Unique constraints, business rules, and role boundaries made explicit.

Decision 1 — User vs GuardProfile

MVP: everything stays in User. The User entity holds identity (email, password), display info (name, phone), and role. Court eligibility is already in a separate CourtEligibility join table. A separate GuardProfile entity would be added in a later version for scheduling-specific employee data such as seniority, hire date, badge number, or certifications — none of which are needed for V1 scheduling logic. Adding GuardProfile later is a straightforward migration: create the table, backfill from User, update relations.

Decision 2 — FairnessRecord: Source of Truth

Two layers, two roles:

  • ShiftAssignment = source of truth for what was assigned. Individual records, always queryable, never deleted after publish.
  • FairnessRecord = source of truth for fairness scoring. Computed from ShiftAssignments at publish time and treated as authoritative thereafter. The scheduling engine reads FairnessRecord for cross-period history — not raw ShiftAssignments — because it is fast, stable, and already aggregated.

If a published schedule is later corrected manually, FairnessRecord must be recalculated for that period. This is an explicit action, not automatic — keeping the boundary clean.

Decision 3 — ShiftType: Enum for MVP

MVP: ShiftType is a Prisma enum (MORNING, EVENING, NIGHT). Display names, hour ranges, and colors live in a code-side config map. A ShiftDefinition DB entity would only be justified if courts need different shift-time definitions or new shift types must be added without a code deploy — neither applies to V1. The enum is easy to extend later; adding a fourth value requires a migration but no structural change.

Unique Constraints & Business Rules

Availability
Availability table
UNIQUE (periodId, userId)
→ one submission per guard per period

AvailabilityEntry table
UNIQUE (availabilityId, date, courtId, shiftType)
→ one entry per guard per day × court × shift
→ prevents duplicate availability rows
ShiftAssignment
UNIQUE (scheduleId, userId, date, shiftType)
→ a guard cannot be assigned the same shift type
twice on the same day, even across courts
(Morning at Court A + Morning at Court B = blocked)

Additional service-layer rules:
→ no Morning + Evening same day
→ no Evening + Night same day
→ no Night day N + Morning day N+1
Opening Duty — Business Rules (Points 4)
DB-level constraints:
CHECK (shiftType = 'MORNING' OR isOpeningDuty = false)
→ opening duty only valid on MORNING shifts
enforced at DB level, not just in code

Partial unique index:
UNIQUE (scheduleId, date, courtId) WHERE isOpeningDuty = true
→ at most one opening duty per court per date
Service-layer rules:
→ opening duty must be assigned to a guard already in that morning slot
→ fairness engine distributes opening duties using FairnessRecord.openingDuties across periods
→ opening duty can be reassigned manually by manager — warning shown if same guard holds it >2× more than peers in rolling history
