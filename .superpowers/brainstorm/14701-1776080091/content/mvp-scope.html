MVP Scope — V1 vs Deferred

What ships in V1. What is explicitly out of scope but designed for. No surprises either way.

V1 — Ships in MVP
Auth & Users
  • Email + password login (NextAuth)
  • Two roles: GUARD, MANAGER
  • Manager creates and manages guard accounts
  • Guard has primary court assigned by manager
Configuration
  • Create/edit courts with shift capacity rules
  • Day-specific capacity overrides (e.g. Friday)
  • System config: weekly minimums, fairness weights
  • Court eligibility per guard
Period & Availability
  • 14-day period lifecycle (DRAFT → OPEN → CLOSED → PUBLISHED)
  • Sunday-start date picker, auto-calculated end date
  • Submission deadline per period
  • Guard submits per-day, per-shift availability (primary court)
  • Auto-save as draft, explicit submit action
  • Editable by guard until deadline
  • Manager sees submission status (submitted / pending)
Schedule Generation
  • 3-pass weighted greedy engine (synchronous, server-side)
  • Pass 1: hard constraint-aware slot filling
  • Pass 2: weekly minimum prioritization (best-effort)
  • Pass 3: opening duty assignment + fairness warnings
  • Deterministic seeded tiebreaker
  • Structured warnings list (UNDERSTAFFED, UNFILLED, MIN_NOT_MET, FAIRNESS)
  • Manager can re-generate (discards draft, reruns engine)
Manager Views
  • Schedule grid: court/shift rows × 14-day columns
  • Warnings panel with severity levels
  • Manual override: add/remove guards, change opening duty
  • Live warning updates after manual edits
  • Per-guard report (secondary view): assignments, shift counts, weekly min compliance
  • Fairness report: distribution of nights/weekends/opening duties vs history
  • Publish confirmation with summary
Guard View
  • Dashboard: period status, submission CTA
  • Availability form: mobile-first, Hebrew RTL, 14-day accordion
  • My schedule: visible only after manager publishes
  • Shows: date, shift, court, opening duty flag
Deferred — Explicitly Out of V1
Notifications
  • Email / SMS / WhatsApp / push notifications
  • Guards check system manually in V1
Multi-Court Availability UI
  • Per-court toggle selection in guard form
  • Schema supports it; UI deferred
  • Default: primary court assumed
Background Jobs
  • Async schedule generation (job queue)
  • Engine is already pure/isolated — wiring is the only V2 change
Guard Data Model
  • GuardProfile entity (seniority, hire date, badge, certifications)
  • ShiftDefinition entity (configurable shift hours per court)
  • Shift preferences (preferred vs available)
Advanced Fairness
  • Auto-apply fairness swaps (V1 only surfaces suggestions)
  • Fairness override audit log (V1 has isManualOverride flag only)
  • Configurable rolling fairness window
Export & Integration
  • PDF / Excel export of schedule
  • Print-friendly schedule view
  • Calendar sync (iCal / Google Calendar)
  • HR system integration
Guard Self-Service
  • Shift swap requests between guards
  • Time-off requests
  • Historical schedule archive for guards
Infrastructure
  • Multi-tenant / multi-organization support
  • Native mobile app (PWA is V2 consideration)
  • SSO / SAML integration
  • Full audit log with revert history
What "designed for but not built" means in practice:
  • Multi-court UI: AvailabilityEntry already has courtId — adding per-court toggles is a UI-only change
  • Background jobs: Scheduling engine has no HTTP dependency — wrapping it in a job runner touches only the API route
  • GuardProfile: Add table, backfill from User, update FK — no scheduling logic changes
  • Notifications: Period lifecycle events are already structured — hooking a mailer is additive
