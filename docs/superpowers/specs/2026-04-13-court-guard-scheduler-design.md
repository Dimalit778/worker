# Court Security Guard Scheduling System — Design Specification

**Date:** 2026-04-13
**Status:** Approved for implementation planning

---

## 1. Product Context

Court security guards submit availability for 2-week scheduling periods. Managers currently build schedules manually — an error-prone, unfair, and time-consuming process.

This system replaces that with a structured workflow:
- Guards submit availability through a simple mobile interface
- The system generates a draft schedule automatically
- Managers review, adjust, and publish the final schedule
- Fairness is tracked cumulatively across periods

**Scale:** 50–150 guards, 5–15 courts, single organization.

---

## 2. Technical Stack

| Layer | Choice | Reason |
|---|---|---|
| Framework | Next.js 14 (App Router) | Single-codebase, two surfaces |
| Language | TypeScript | Type safety throughout |
| UI | Tailwind CSS + shadcn/ui | Rapid, consistent RTL-capable UI |
| Auth | NextAuth (email + password) | Simple, no vendor lock-in |
| ORM | Prisma | Type-safe, transaction support, migrations |
| Database | PostgreSQL (Neon or Railway) | Full SQL power for scheduling logic |
| Locale | Hebrew (RTL) | Primary language |
| Device target | Guards: mobile-first. Managers: desktop | Two distinct UX surfaces |

### Architecture Principles

- **Thin API routes:** Parse request, check auth, call service, return result. No business logic in routes.
- **Domain service modules** in `lib/services/`: `scheduling/`, `availability/`, `guards/`, `periods/`, `admin/`, `fairness/`, `validations/`
- **Repository pattern** in `lib/db/`: services call repositories, never Prisma directly
- **Scheduling engine:** Pure TypeScript function — no HTTP, no side effects. Callable from API route in V1; extractable to background job in V2 with no engine changes

**Call chain:** HTTP Request → API Route → Service Module → Repository → Prisma → PostgreSQL

## 3. Scheduling Period Structure

- Exactly 14 days: always starts Sunday, ends Saturday of the following week
- Week 1: days 1–7 (Sunday–Saturday)
- Week 2: days 8–14 (Sunday–Saturday)
- Every displayed date shows weekday name + exact date in Hebrew

## 5. Data Model

### Core Entities

**User**
```
id, email, passwordHash, name, phone
role: GUARD | MANAGER
primaryCourtId → Court (nullable, FK)
isActive, createdAt
```

**Court**
```
id, name, code, isActive
→ ShiftCapacityRule[]
→ CourtEligibility[]
```

**CourtEligibility** (guard ↔ court many-to-many)
```
id, userId → User, courtId → Court
```

**ShiftCapacityRule**
```
id, courtId → Court
shiftType: MORNING | EVENING | NIGHT
dayOfWeek: 0–6 | null (null = applies all days)
minStaff, maxStaff
```

**SchedulingPeriod**
```
id, name
startDate (Sunday), endDate (Saturday + 13 days)
submissionDeadline
status: DRAFT | OPEN | CLOSED | PUBLISHED
createdBy → User
```
*`SchedulingPeriod.status` tracks the **submission and publication lifecycle** of the period itself:*
- *DRAFT — created by manager, not yet open to guards*
- *OPEN — guards can submit and edit availability*
- *CLOSED — submissions locked; schedule generation is now possible*
- *PUBLISHED — the final schedule has been published; guards can view their assignments*

*`Schedule.status` tracks the **generation lifecycle** of a single schedule document within a closed period:*
- *DRAFT — generated by the engine, under manager review; may be discarded and regenerated*
- *PUBLISHED — approved and published by the manager; triggers FairnessRecord materialization*

*A period in CLOSED status may have zero or more Schedule records (zero before first generation, one DRAFT during review, one PUBLISHED after approval). A period moves to PUBLISHED only after its Schedule is published.*

**Availability**
```
id, periodId → SchedulingPeriod, userId → User
submittedAt, isSubmitted
UNIQUE (periodId, userId)
→ AvailabilityEntry[]
```

**AvailabilityEntry**
```
id, availabilityId → Availability
date, courtId → Court, shiftType
isAvailable (bool)
UNIQUE (availabilityId, date, courtId, shiftType)
```
*In V1, `courtId` is auto-derived from the submitting guard's `primaryCourtId` by the availability service. The guard never selects a court in the UI. The field remains explicit in the schema so that multi-court submissions (a future extension) require no schema change.*

**Schedule**
```
id, periodId → SchedulingPeriod
status: DRAFT | PUBLISHED
generatedAt, publishedAt, generatedBy → User
→ ShiftAssignment[]
→ ScheduleWarning[]
```

**ShiftAssignment**
```
id, scheduleId → Schedule
userId → User, courtId → Court
date, shiftType: MORNING | EVENING | NIGHT
isOpeningDuty (bool)
isManualOverride (bool)
createdAt
UNIQUE (scheduleId, userId, date, shiftType)
CHECK (shiftType = 'MORNING' OR isOpeningDuty = false)
PARTIAL UNIQUE INDEX: (scheduleId, date, courtId) WHERE isOpeningDuty = true
```
**V1 audit trail for manual edits:** `isManualOverride = true` is set on any `ShiftAssignment` that was added or modified by a manager after generation. Deletions are hard deletes — no record is kept of what was removed. This is sufficient for V1 reporting (manager can see which assignments were auto-generated vs manually placed) but does not provide a full change history.

*Deferred: full audit log (who changed what, when, from what value to what value) and the ability to revert manual edits. These require an `AuditLog` table and are explicitly out of V1 scope.*

**ScheduleWarning**
```
id, scheduleId → Schedule
type: UNDERSTAFFED | UNFILLED | MIN_NOT_MET | CONFLICT | FAIRNESS
severity: ERROR | WARNING | INFO
courtId? → Court, userId? → User, date?
message (human-readable Hebrew)
```
*Warning type definitions:*
- *`UNDERSTAFFED` — a slot was filled, but with fewer guards than `minStaff`. Some guards are assigned; the slot is partially covered.*
- *`UNFILLED` — a slot has zero guards assigned. No eligible, conflict-free guard was available for this slot at all. The slot is completely uncovered.*
- *`MIN_NOT_MET` — a guard did not receive the minimum required morning or evening shifts for a given week, despite best-effort Pass 2 assignment.*
- *`CONFLICT` — a manual edit introduced a shift conflict (same-day incompatible shifts or Night → Morning). Emitted post-edit, not by the engine.*
- *`FAIRNESS` — a guard's assignment count in a tracked dimension (nights, weekends, opening duties) exceeds the team average by more than the configured threshold.*

**FairnessRecord**
```
id, userId → User, periodId → SchedulingPeriod
totalShifts, morningShifts, eveningShifts, nightShifts
weekendShifts, openingDuties
UNIQUE (userId, periodId)
```
*Materialized at publish time from ShiftAssignment data. Authoritative source for cross-period fairness scoring. Recalculated explicitly if a published schedule is later corrected.*

**SystemConfig**
```
key (unique), value (JSON)
Examples:
  weekly_min_morning: 2
  weekly_min_evening: 1
  fairness_weights: { W1: 3, W2: 2, W3: 1, W4: 1 }
  fairness_shift_threshold: 2       (night/weekend excess before FAIRNESS WARNING)
  fairness_opening_duty_threshold: 2 (opening duty excess before FAIRNESS INFO)
```

### ShiftType

Prisma enum: `MORNING | EVENING | NIGHT`. Display names, hour ranges, and colors live in a code-side config map. A `ShiftDefinition` entity is deferred to a later version.

### Constraint Enforcement

| Rule | DB | Service | UI Warning |
|---|---|---|---|
| One submission per guard per period | UNIQUE | ✓ | — |
| No duplicate availability entries | UNIQUE | — | — |
| No same shift type twice in one day | UNIQUE | ✓ | ✓ |
| No Morning + Evening same day | — | ✓ | ✓ |
| No Evening + Night same day | — | ✓ | ✓ |
| No Night → Morning next day | — | ✓ | ✓ |
| Opening duty only on MORNING | CHECK | ✓ | ✓ |
| One opening duty per court per date | Partial index | ✓ | ✓ |

## 6. User Flows

### Guard Flow (5 steps)
1. **Login** — email + password
2. **Dashboard** — see active period, submission deadline, status (Draft / Submitted / Awaiting schedule / Published)
3. **Availability form** — 14-day accordion; per-day, per-shift toggles for primary court; auto-save; explicit submit button
4. **Editable** until deadline; read-only after
5. **My schedule** — visible only after manager publishes; shows date, shift, court, opening duty flag

### Manager Flow (7 steps)
1. **Create period** — Sunday-only date picker, 14-day auto end, submission deadline; period starts as DRAFT; manager explicitly opens it (→ OPEN) to allow guard submissions
2. **Monitor submissions** — guard list with submitted/pending status, view each submission
3. **Close & generate** — manager triggers generation; period → CLOSED (guards can no longer edit); engine runs 3 passes synchronously; returns draft + warnings. If re-generation is triggered, the existing draft is discarded and the engine runs fresh from current availability data.
4. **Review grid** — court/shift rows × 14 columns; warnings panel; can re-generate as many times as needed before publishing
5. **Manual adjustments** — add/remove guards, change opening duty; live warning updates
6. **Review reports** — per-guard report, fairness distribution
7. **Publish** — confirmation dialog; FairnessRecord materialized; guards see schedule

## 7. Guard Availability UX

**Mobile-first, Hebrew RTL.**

- **Accordion-style:** One day expands at a time. Collapsed rows show a color dot (green = has availability, grey = unavailable).
- **3 toggles per expanded day:** בוקר / ערב / לילה — for the guard's primary court. No court selection needed.
- **Auto-save as draft** on every toggle. Submit button explicitly marks as submitted.
- **Progress bar** always visible at bottom: "X / 14 ימים מולאו".
- **Primary court shown in header** for context only (not selectable in V1).

## 8. Manager Schedule Grid

**Desktop, Hebrew RTL.**

- **Rows:** Grouped by court (collapsible court sections), with sub-rows for Morning / Evening / Night
- **Columns:** 14 days; weekends tinted amber
- **Cells:** Guard name chips per shift slot. ★ = opening duty. Capacity counter "filled/max" in cell header. Red cells = understaffed or empty, with dashed "+ הוסף" button.
- **Color coding:** Green = morning, purple = evening, dark = night, red = warning
- **Warnings panel:** Right side, structured warnings with severity. Clickable to jump to relevant cell.
- **Manual edit:** Click any cell to add/remove guard or change opening duty. Live warning recalculation.

**Secondary view — Per-Guard Report:**
A separate manager screen (not the main grid) showing each guard's full assignment list, shift type counts, weekly minimum compliance per week, and fairness stats vs team average.

## 9. Scheduling Algorithm

### Inputs
- AvailabilityEntry records for the period
- ShiftCapacityRule records
- CourtEligibility records
- FairnessRecord history (all past periods)
- SystemConfig (weekly minimums, fairness weights)
- Period date range (14 days, split by week)

### Outputs
- `ShiftAssignment[]` — the draft
- `ScheduleWarning[]` — structured warnings with severity

### Pass 1 — Slot Filling (Hard Constraints)

Iterate over every (court, date, shiftType) slot, ordered by **most-constrained first** (fewest available guards):

1. Get all guards available for this slot (from AvailabilityEntry matching court + date + shift, scoped to primary court for V1)
2. **Exclude** guards violating hard conflict rules (checked across all courts, not just the current court):
   - Already has Morning this day (at any court) → exclude from Evening
   - Already has Evening this day (at any court) → exclude from Night
   - Had Night yesterday (at any court) → exclude from Morning today
3. **Score** remaining candidates:
   - `+W1` fewer total assigned shifts this period vs. average
   - `+W2` fewer night shifts historically (FairnessRecord)
   - `+W3` fewer weekend shifts historically
   - `+W4` weekend slot + guard has below-average weekend count
   - **Deterministic tiebreaker:** stable hash of `(guardId + periodId + date + shiftType)` — reproducible, not random
4. **Assign** top-scored guards up to `maxStaff`
5. If below `minStaff` → emit `UNDERSTAFFED` warning; assign all available

### Pass 2 — Weekly Minimum Prioritization (Best-Effort)

For each guard × each week (Week 1, Week 2):
1. Count current morning and evening assignments in that week from the draft
2. If morning count < `weekly_min_morning` (default: 2): find available, conflict-free morning slots with remaining capacity in that week → assign
3. If evening count < `weekly_min_evening` (default: 1): same logic for evenings
4. **Never overrides Pass 1 assignments** — only adds into slots with remaining capacity
5. **Never overfills capacity** — a slot will not be assigned beyond its `maxStaff` limit to satisfy a weekly minimum. If all suitable slots for a guard in a week are already at capacity, the minimum cannot be met and a warning is emitted instead.
6. If minimum unreachable (no suitable slots, or all slots at capacity) → emit `MIN_NOT_MET` warning with guard name, week number, and shift type

### Pass 3 — Opening Duty + Fairness Warnings

**Opening duty assignment:**
1. For every morning slot, designate one guard as opening duty
2. Sort morning guards in the slot by `FairnessRecord.openingDuties` ascending
3. Assign the guard with fewest cumulative opening duties
4. Emit `FAIRNESS` INFO warning if selected guard's opening duty count exceeds team average by more than `fairness_opening_duty_threshold` (configurable via SystemConfig, default: 2)

**Fairness warnings:**
1. Compute draft totals per guard: total shifts, nights, weekends
2. For any guard whose night or weekend count exceeds team average by more than `fairness_shift_threshold` (configurable via SystemConfig, default: 2) → emit `FAIRNESS` WARNING
3. If a valid swap exists (another guard in the same slot with a lower count), surface it as a suggestion for the manager — never auto-apply
4. Pass 3 never changes assignments unilaterally

## 10. Fairness System

**Cross-period cumulative tracking.** FairnessRecord stores per-guard, per-period counts of: total shifts, morning, evening, night, weekend, opening duties.

**`ShiftAssignment` is the operational source of truth** — the definitive record of what was assigned for each shift slot. It is never deleted after publishing and is the basis for all correctness checks.

**`FairnessRecord` is the materialized historical scoring and reporting source** — pre-aggregated per-guard, per-period counts derived from ShiftAssignments at publish time. The scheduling engine reads FairnessRecord for cross-period fairness scoring because it is fast and stable. Reports read it for the same reason. It is not a live view; it reflects the state of the schedule at the moment of publication. If a published schedule is later corrected manually, FairnessRecord for that period must be explicitly recalculated — it does not update automatically.

**Fairness dimensions tracked:**
- Total shifts per period
- Night shift count (cumulative)
- Weekend shift count (cumulative)
- Opening duty count (cumulative)
- Weekly minimum compliance per week

## 12. MVP Scope

### In V1
- Email/password auth, two roles (GUARD, MANAGER)
- Manager creates/manages guard accounts and primary court assignment
- Courts, shift capacity rules, court eligibility configuration
- System config (weekly minimums, fairness weights)
- 14-day period lifecycle (DRAFT → OPEN → CLOSED → PUBLISHED)
- Guard availability submission (primary court, per-day per-shift, auto-save, explicit submit)
- 3-pass scheduling engine (synchronous, server-side)
- Deterministic seeded tiebreaker
- Structured warning system (UNDERSTAFFED, UNFILLED, MIN_NOT_MET, CONFLICT, FAIRNESS)
- Manager schedule grid with manual override and live warning updates
- Per-guard report and fairness report
- Cross-period FairnessRecord materialized on publish
- Guard published schedule view (visible only after publish)
- Hebrew RTL throughout, mobile-first guard UI

### Explicitly Deferred
- Notifications (email/SMS/WhatsApp/push)
- Multi-court availability UI (schema supports it; UI deferred)
- Background job scheduling (engine is ready; wiring deferred)
- GuardProfile entity (seniority, hire date, badge, certifications)
- ShiftDefinition entity (configurable shift hours per court)
- Shift preferences (preferred vs available)
- Auto-apply fairness swaps (V1 surfaces suggestions only)
- Full audit log with revert history
- PDF/Excel export, calendar sync
- Shift swap requests between guards
- Multi-tenant / multi-organization
- SSO / SAML
- Native mobile app / PWA
